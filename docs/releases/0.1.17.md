# 0.1.17

Moved from the release notes on 2026-11-20: the user wants the notes to hold only New and Fixes.

- Released 6 days after 0.1.16: fixes the user reported were ready: Chinese fonts drawn in brush faces, slideshow keys that did nothing, dragging objects in ElyShow, and an extra shape drawn after inserting one.
- 1 fix was made after its last review failed and has not been reviewed again (R15.11g); its review needs a Windows machine with Microsoft Office. R15.11 and R15.11c, counted here before, passed review round 4 under R19.3 (a3eab32d, 2026-11-20).
- 33 tasks used up their review rounds or wait on something outside the project; each is marked `[!]` in `tasks/TASKS.md` with what is left.
- Dragging objects in ElyShow needs kernel patch 0140; it is tested on Linux and macOS, not yet by hand on Windows. The slideshow keys were fixed for the case reproduced here; the conditions of the user's report were not reproduced.
- Kernel patches 0132 to 0146, MuPDF patches 0009 to 0011, gpui-pre 0.3.12 with patches 0014 to 0015.
- No arm64 builds for Linux or Windows.
- Known issue: typing on in one long ElyDoc paragraph grows the engine's memory, about 16 MB per 100 edits, until the document closes. The kernel fix (R20.54) slowed typing and is not in this release.

## Shipped code after the measured builds

The Windows records measured the 8014ab6b tree, installed from the dist17f setup (packed kernel b8c76f72); the macOS records measured the package built at 6e9e118d (source kernel 1c8c756c, installed kernel ad8115f0). These are every commit since 6aee0f1d under apps/, crates/, vendor/, patches/, packaging/, Cargo.toml and Cargo.lock; "in" names the measured trees that already hold it.

- 58fe2961 (R20.51, in both): kernel test modules only, compiled for tests and in no release binary.
- 3382c111 (R20.79, in Windows): Linux AppImage launcher only; one `grep` of a unit file per AppImage start.
- 97a2dbc1 (R20.79, in Windows): Linux only; the cleanup of an AppImage's shadowing engine unit, moved off the start path in fb20ff2b.
- 4eeac0ab (R20.79, in Windows): Linux only; the same cleanup's test of the unit line, and the launcher's.

- 8014ab6b (R20.88, in Windows): the frames journal, behind the `frames` feature, which no release build turns on.
- fed4db8d (R20.79): Linux only; the cleanup survives concurrent starts.
- 3c844f14 (R20.88): the frames journal and its test, behind the same feature.
- 99633b8f (R20.79): Linux only; the cleanup reloads once even if another start removed the unit.
- 3a4c1c54 (R20.74): the worker logs each start stage, reading the OS's counters four times, which costs microseconds; the Windows `windows-sys` feature only adds bindings.
- 967d28cd (R20.74, freeze exception): the same stage logs take their lock without `expect`; on a poisoned lock a stage line is skipped with a warning, so the behaviour is identical unless the lock is poisoned.
- fb20ff2b (R20.79, Linux only): the cleanup runs once per run on its own thread after the engine is taken, so the start never waits on it, `rpm -q` included; macOS and Windows code is unchanged.
- f39211a3 (R20.96, Windows only, freeze exception): stopping a Git in ElyTree ends only processes started no earlier than their parent, so a reused parent id no longer takes in explorer and the programs started from it; a process whose start time cannot be read is logged and left running. Stopping Git is not a timed case. Not yet built or tested on Windows: that is job 1b on the test VM, and the v0.1.17 tag waits for it.
