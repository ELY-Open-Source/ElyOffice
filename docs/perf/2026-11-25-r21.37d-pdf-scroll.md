# ElyPDF wheel scrolling, R21.37d (#113)

`tests/perf/pdfscroll.py`, 2026-11-25. Wheel passes: steady 60 notches 50 ms apart, flick 150 notches 8 ms apart, down then up. Samples: 1000 pages of images, 1000 pages of text, 300 pages of vector drawing. Frame times come from gpui's profiler (`ely-ui/frames`): dirty is when the view changed, then draw start, draw end and shown.

## Findings

- ElyPDF draws a frame in 2–4 ms on every machine and every sample. No frame was lost and the main thread never stalled.
- Page content makes no difference: images, text and vectors give the same times.
- Mac M4 (Metal, 60 Hz): draw end to shown 0.1 ms; every frame shows on the next refresh, the limit of a 60 Hz screen. "Late" only means the screen is not 120 Hz.
- 7877 (Windows, no GPU, WARP): draw end to shown under 1 ms, but frames wait 22–40 ms (p95) to start drawing. gpui paces Windows frames by `DwmFlush` (`vendor/gpui-pre-windows/src/vsync.rs`). Timed directly in the same desktop session, `DwmFlush` returns every 20 ms (p50), 35 ms (p95) before ElyPDF starts, and 18–22 ms (p50), 20–42 ms (p95) during the whole scroll run. The compositor's own clock, about 45 Hz without a GPU, sets the pace, not ElyPDF.
- Omarchy (llvmpipe): CPU rasterisation of the window takes 11–19 ms (p95). ElyMark, scrolled the same way on the same machine, takes 6.5–10 ms (p95) draw end to shown and 17–25 ms dirty to shown: no Ely window reaches 120 FPS on llvmpipe. ElyPDF's extra few ms is sampling a window full of page textures; its tiles are already rendered at device pixels and drawn 1:1 (`backdrop.rs`, `pages.rs`), one set per page, without scaling or overdraw.
