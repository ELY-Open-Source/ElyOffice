# 常设决定的细则

`agents.md` 的“常设决定”每条只写规定，这里是每条的全文（实现、范围、任务编号）。按日期的完整记录在 `docs/decisions.md`。改了一条，两处一起改。

## 常设决定

- 上游：LibreOffice 26.2.6、MuPDF 1.28.5、Git 2.56.0 加 git-lfs 3.8.0、`gpui-pre` =0.3.14，以 `scripts/fetch-references.sh` 为准；组件库跟随其 main，修复在组件库仓库里做并推上去，再改 pin。
- 仓库与发布在 GitHub 组织 ELY-Open-Source（ElyOffice、Ely-GPUI-Components）。推 `v*` 标签即运行 `.github/workflows/release.yml`：自托管机器上以 `scripts/ci.sh` 构建 macOS（arm64，Rosetta 下的 Intel）、Windows、Linux x86_64（Omarchy 的 AlmaLinux 8 容器）并上传，Linux 与 Windows 都不出 arm64（用户 2026-11-16 定，R20.2），GitHub 托管的机器不建发布；四个任务互不等待。`ci.sh` 先过门，不过即不建：更新日志只有新功能与修复两节，发布记录 `docs/releases/<版本>.md` 写明 `[~]` 的数目、距上一版不足七天的原因（`scripts/release-gate.py`，用户 2026-11-20 定），本系统有这一版的基准记录与安装后首次打开的记录，Windows 另有重启后的（`tests/perf/firsts.py`；用户 2026-11-20 定；0.1.17 的 macOS 与 Linux 沿用 0.1.16 的基准记录，Linux 不要装后首开），慢过三成的各有原因（`tests/perf/baseline.py`），该提交的 `pr.yml` 已通过；打包前再以 `scripts/release-tests.sh` 跑全部测试（`ELY_REQUIRE_ENGINES=1`），其中空闲引擎静置 400 秒后十分钟 CPU 为 0（Windows 不超 `idle.json` 里记录周期的两倍，R20.13）、内存不超 `tests/perf/idle.json` 一成（`tests/perf/idle.py`）；最先上传的平台把发布建成预发布，四端都上传、核对过后再改为正式并设为最新（`releases/latest` 是官网下载与应用更新所读）；源码包只由 x86_64 的 Linux 上传。引擎经 `ELY_SHARE` 共用，新的 LibreOffice 补丁须先在三台机器的共享引擎上重建；macOS 上 `ci.sh` 须 bash 5，拒绝 3.2（R15.61）。
- 构建一律用 [huacnlee/cargo](https://huacnlee.github.io/cargo/)（替换 `cargo`）：中间产物在 `~/.cargo/targets/`，各工作树与项目共用、自动限额，二进制仍在 `./target`；它忽略 `--target-dir`、`CARGO_TARGET_DIR` 并告警，故基准工具先建 frames 版、复制到 `target/frames`，再建发行版。它的测试程序不在 `./target` 下，找不到旁边的 worker：带内核的单测须设 `ELY_LOK_WORKER`、`ELY_PDF_WORKER`（`release-tests.sh` 自己设）；`cargo check` 与 clippy 须设 `CARGO_CHECK_SHARED_DEPS=0`，否则两份 gpui 混用、类型对不上。发布的 `ci.sh` 先核对本机（Linux 另核构建容器）的 `cargo --version` 带 `huacnlee/cargo`，不带即报错退出；AlmaLinux 8 容器的 glibc 2.28 跑不了其发布版（要 2.34），镜像里以 Rust 1.100 从钉住的提交建，产物与本机同在 `target/release`。PR 的机器（GitHub 托管）是标准 Cargo，脚本两者都得过。
- Git：main 的历史不改写；提交签名，不写任何署名行。
- 许可：自有代码 MIT；随包引擎照各自的许可，Linux 包的许可字段取 `packaging/apps.tsv`。
- macOS 发布以 Developer ID 签名并公证（`ELY_SIGN_IDENTITY`、`ELY_NOTARY_PROFILE`），缺即失败，不出未公证的包。
- 首批发布 ElyDoc、ElyTable、ElyShow、ElyPDF、ElyMail、ElyTree、ElyMark；ElyAgent 第二批，加进同一个包；用户 2026-11-19 定先不做，C15 暂缓到用户重开。
- 安装包（2026-11-14 用户定，SF.6、SF.7、SF.19、SF.21）：每个平台一个 ElyOffice 安装包，不出单个应用的包；Windows 是 `ElyOffice-<版本>-windows-x86_64-setup.exe`，组件页七个应用各一个勾、默认全选，“应用和功能”只一项；macOS 是签名并公证的 `.pkg`（Developer ID Installer），“自定”页七个勾，关掉可重定位；Linux 只有 `ely-office` 包与统一的 AppImage，全部装上；WinGet 一份 `ZacharyZhang.ElyOffice`。Doc、Table、Show 共用一份内核（Windows `%LOCALAPPDATA%\Programs\Ely Office\Kernel`，macOS `/Library/Application Support/Ely Office/Kernel`，Linux `/opt/ely-office`，AppImage 解到 `~/.local/lib/ely-office/<编号>`）；内核、常驻引擎与登录项是隐藏组件，三个文档应用都没选时不装。
- 常驻引擎（2026-11-14 用户定，SF.3、SF.4、SF.8、SF.20、SF.22）：登录后每个已装的文档应用常驻一个已过自检的空闲引擎，三端都做，不给开关；Windows 用当前用户的 `Run` 值“Ely Office”，指向内核旁的 `ely-login.exe`，它给每个已装的文档应用依次跑 `engine`（`ely-login stop` 即 `engine stop`），日志在数据根的 `ely-login.log`；`ely-login.exe` 只在内核的 `program\ely-kernel-id` 与安装清单 `.ely-installed` 都在时才算 Ely 的，否则不跑、不写 `Run` 值；安装与卸载程序动文件前跑 `ely-login stop`，停不下即退出码 2、不动文件；完成后写 `Run` 值并跑 `ely-login` 预热，失败即提示并退出码 2；内核删去时 `Run` 值随之删；macOS 用 `/Library/LaunchAgents/ely.zacharyzhang.office.login.plist`，指向 `/Library/Application Support/Ely Office/ely-login`（在内核外，随内核这一隐藏选项装），`AbandonProcessGroup` 使它退出时引擎不随之结束；它只起 `/Applications` 里带 `Contents/Helpers/Ely Engine.app` 且版本与自己相同的文档应用（自定时没选的旧版跳过）；`.pkg` 换内核前以控制台用户跑旧的 `ely-login stop`，停不下即退出码 2、不动文件；装完以该用户同步预热，再重新载入代理；Linux 用 systemd 用户单元模板 `ely-engine@.service`，Doc、Table、Show 各一个实例，挂在 `graphical-session.target`（`Type=oneshot`、`RemainAfterExit`，`ExecStart` 为 `<应用> engine`，`ExecStop` 为 `engine stop`，`KillMode=process`：停单元只结束空闲的，应用接管的引擎不随之结束）；包装到 `/usr/lib/systemd/user`，装后脚本在 `/etc/systemd/user/graphical-session.target.wants` 写三个链接（即 `systemctl --global enable` 写的，容器与没有 systemd 不认带特殊字符的程序路径），文件挪了即改写，缺的链接每次补上，写了或补了即 `systemctl --user daemon-reload`，没有 systemctl 或重载失败即记一行，不拦应用；物理内存 8 GB 起每个应用一个，4 至 8 GB 只给最近用过的，不到 4 GB 不常驻；空闲引擎只在端点上阻塞，不占 CPU（Windows 上系统库的定时上报约十分钟一千二至二千二百万周期，R20.13）；不在时应用自己起，日志记一行。`<应用> engine` 一次只跑一个（数据根下的 `starting.lock`），轮到时才看内存与最近用过；它从起 worker 到交出一直持配置目录的 `starting.lock`，应用见此锁即等，已有自检过的空闲引擎即退出 0，否则自己起，失败退出 1。它以 `--idle idle-<应用>-<配置目录规范化路径的散列>` 起 worker（数据文件夹不同即不同的引擎）：它先持配置目录里的 `idle.lock`（一个应用只一个；只读探测不取锁），即在该名字上听，再在私有名字上等该命令连上跑自检，自检者发 RELEASE 后断开、命令退出；起者连上之前一直持着 worker 的标准输入，它先于连接关闭即 worker 退出（不留占锁的孤儿）；引擎的标准错误写数据目录的 `engine.log`。应用经 `Worker::take` 在起进程的线程上接管：连公开名字，握手的回答到自检完才来；连不上而两把锁有一把被持有即在起，每 100 毫秒再试，锁空闲、握手不符或已被别的应用接管即自己起；`engine stop` 同此，无空闲引擎不报错。接管后释放名字与锁。接管的引擎从不按进程号结束：Windows 用连接时打开的进程句柄，macOS、Linux 断开连接，引擎见断开 10 秒内必退出。4 至 8 GB 时起一个即先停其余应用的空闲引擎。文档的首个图块画出后，应用起一次 `<应用> engine` 作接班的。空闲引擎以后台优先级起，接管时、回答应用之前恢复正常：Windows 后台模式（连磁盘），macOS `PRIO_DARWIN_BG`，Linux 自成会话、自动组 nice 19 与空闲 I/O 类（普通用户的 nice 改不回，自动组可以；内核对自动组的写全系统每 100 毫秒一次，遇 EAGAIN 重试）。“最近用过”是各应用数据目录里 `engine-used` 的修改时间，应用开文档时写。每个引擎的临时目录是配置目录下的 `tmp/<私有名>`，退出时只删自己的。
- 横幅（2026-11-14 用户定，SF.13–SF.15）：只留 ElyDoc 的字体缺失（`doc-fonts`）；其余信息去状态栏的一项、出后果那一刻的对话框、页面位置的错误页或 toast，规则 2 不变。
- 数据只在 `ely_platform::data_dir` 给出的目录；用户文档永不碰；卸载先问。根默认在系统的本地数据目录；设置“存储”可换到所选文件夹下的 `ElyOffice`，指向文件 `folder.json` 留在默认位置，下次启动、无 Ely 应用在运行时搬动（`ely_platform::folder`）。
- 文件类型只写在 `packaging/types.tsv`，只进“打开方式”，从不设为默认（Windows 的“新建”只在该类型无任何处理程序时设）。URL 方案也写在那里，第二列以冒号结尾（`mailto:`）：Linux 的 `x-scheme-handler` 与 `%U`，Windows 的 `Capabilities\URLAssociations` 与 `RegisteredApplications`（只进“默认应用”供选，从不写 `Classes\mailto`），macOS 的 `CFBundleURLTypes`；链接经 `ely_ui::mail_link` 原样交到应用，ElyMail 以引擎的 `mailto` 照 RFC 6068 填好新信（引号里的逗号不切、域名转 IDNA、主题解 MIME 编码词）。“打开方式”里不得出现 LibreOffice，任何脚本都不挂载 LibreOffice 镜像。
- 语言：界面英文、简体中文、西班牙语（es-ES，系统 es-* 同用）、法语（fr-FR，系统 fr-* 同用）、德语（de-DE，“Deutsch”，系统 de-* 同用）、日语（ja-JP，系统 ja-* 同用）、韩语（ko-KR，系统 ko-* 同用）与越南语（vi-VN，“Tiếng Việt”，系统 vi-* 同用），每个应用各语言都全，任一目录缺键即失败，不以英文补；英文、中文以外的六种未经母语者校对，设置里标“预览”（`docs/accessibility.md` 的“译文校对”）；内核界面固定英文，内核给出的固定文字（ElyTable 的状态与错误、单元格样式，ElyDoc 的内置样式名）由 Ely 按界面语言重写，译文照 LibreOffice 26.2.6.3 该语言的译文，文件与主题资源自带的名字（母版、主题色集、用户样式、字体）照原样；ElyTable 导入非 UTF-8 的文本时预选界面语言的 Windows 代码页（中文 GB18030，日文 Windows-932，韩文 Windows-949，西欧各语 Windows-1252，越南文 Windows-1258）；ElyTable 公式为 Excel A1、数字按 en-US；拼写词典只随英文。
- 外观：Doc、Table、Show、PDF 的页面照文件原色，只有四周的界面随深浅色；邮件正文、Mark、Agent 随深浅色。深色底 `#252525`，不用纯黑。有 Omarchy 时随 Omarchy。
- 性能：八个应用都不许卡顿（120 FPS 手感，potato computer 也要流畅），输入延迟与帧时间实测验收；界面线程不等内核、不持 worker 锁，空闲不做事；ElyDoc、ElyTable、ElyShow 的就地保存在下一次打字停顿（500 毫秒无键）开始，至多等 2 秒，期间打的键一并存下（R15.37）；恢复点给等着的键与图块让路（补丁 0090、0106），同一标签让路满 60 秒后下一次不让（R15.56）；命令行读的副本、用户的保存、另存为与自动保存从不让路；前台以外的用户文件首次显示（或别的程序问到）才载入，视图的输入与其图块先于排队的后台工作（R15.57）；渲染器为软件模拟（WARP、llvmpipe）时按减少动效，设置里明选完整动效除外，次序为环境变量，再 Ely 的明选设置，其后系统要求减少或渲染器为软件，有一即减少（R20.63）。
- LOK：worker 启动时关掉内核的 OpenCL（`SAL_DISABLE_OPENCL=1`：其启动自检在 AMD 驱动里会卡死，Calc 在 CPU 上算）与打印机查找（`SAL_DISABLE_PRINTERLIST`、`SAL_DISABLE_DEFAULTPRINTER`：Windows 上每次载入问 spooler 约 0.5 秒，Ely 打印走 PDF，SF.18；点名打印机或按打印机度量排版的文档才问，补丁 0133）；界面只经 `ely_lok::commands::COMMANDS` 发 UNO 命令；外部链接打开时显示保存的值，用户点状态栏或菜单的“更新链接”才经 `.uno:ElyUpdateLinks` 读源，源之后再存即在状态栏说明（`ely_office::Linking`）；内核弹出的对话框即刻关闭并报错，需要的对话框由 Ely 自建；内核改动只以 `patches/libreoffice` 的补丁序列进入，其日志用 `ELY_WARN` 等（补丁 0108），经 worker 的 stderr 进应用日志。
- 通道（2026-11-14 用户定，SF.3）：worker 起来后在只给本用户的端点上听，应用自己起的也一样，只此一路。Windows 是两条单向命名管道 `\\.\pipe\ely-office-<SID>-<名字>-in|out`，DACL 只许本用户，首个实例（空闲引擎的名字除外：不限实例数，好让接班的在被接管的还连着时就听）、拒远程，应用核对管道的服务进程即所起的 worker（接管空闲引擎时核对它是本用户的进程，且即 HELLO 回答里的进程号）；客户端只许服务端识别、不许冒用身份；macOS、Linux 是 0700 文件夹里的 0600 套接字（Linux 在 `$XDG_RUNTIME_DIR/ely-office`，macOS 在系统给本用户的临时文件夹，不读 `TMPDIR`：worker 的 `TMPDIR` 指向内核自己的临时目录）。worker 绑好后在标准输出写一行 `ely-lok-worker: listening`，之后标准输出并入标准错误；应用连上先发 HELLO（版本、内核编号），不符即 ERR 并退出。内核编号是 `scripts/kernel-id.sh` 对内核目录各文件的 SHA-256，写在版本文件旁的 `ely-kernel-id`（`build-libreoffice.sh`、`stage.sh`、`extract-official-lo.sh` 写；缺即启动失败）。`ely-ipc` 帧格式不变。
- 更新：每个平台一份清单，更新整套（应用与内核一起换），读 GitHub 的最新发布（`releases/latest/download`，不调 API），不通则读官网转发的同一路径；清单以 ed25519 签名（`<清单>.sig`，签的是文件名加内容），公钥编进应用（`ely_platform::update::KEY`），缺签名或不符即拒；种子是组织机密 `ELY_UPDATE_KEY`，本机副本 `update-key.txt` 不入库，丢失即旧版再也收不到更新；自动检查默认关，从不静默安装；包管理器与 Nix 装的不自更新，只提示（Nix 以 toast）。清单名 `ely-office-<平台>.json`（`packaging/manifest.sh`）；Windows 另发 0.1.16 读的每应用清单，都指统一安装程序；Linux 的 AppImage、deb、rpm、Arch 包都读 `ely-office-linux-x86_64.json`，指统一的 AppImage；0.1.16 的七个 AppImage 读的每应用清单照发，同指它（SF.21）；macOS 发 `ely-office-macos-<aarch64|x86_64>.json`，指 `.pkg`，下载后待应用退出交给“安装器”（`open -b com.apple.installer`），打不开即写一条说明，下次启动显示。重新启动以更新前，别的 Ely 应用开着即列出（`ely_platform::instance::open_besides`），由用户关，不代关；Windows 的常驻引擎由安装程序先停。
- 每个应用只跑一份，再次启动把文件交给运行中的那份。
- 本机别的程序经命令行读写已打开的文档（#107，R21.25–R21.36）。四个应用共用 `docs`、`open`、`new`、`export`、`save`，任一参数写 `-` 读标准输入，退出码 0 成功、1 失败、2 用法不对、3 未运行。ElyTable：`cell`、`range get|set|merge|unmerge`、`format`、`sheet list|add|remove|rename|freeze`、`rows|columns insert|delete|height|width`，按地址（内核补丁 0058、0150–0152）。ElyDoc：`text get|replace|append`、`format`、`table insert`、`image insert`（0153–0156）。ElyShow：`text get|replace|set`、`notes get|set`、`slide list|add|duplicate|delete|move`、`image insert`，按页号（0157–0159）。ElyMark：`text get|replace|set|append`。请求走实例门（本机回环、令牌文件只给同一用户），由应用以 `ely_ui::on_ask` 作答，始终开着；每次改动一步撤销（Impress 的替换每个改到的文本框一步），不动用户的光标、选区与所在幻灯片；替换是精确、区分大小写的全部替换；ElyMark 读写此刻的 Markdown 原文（含未写回的键入），预览模式拒绝。ElyPDF 有意不设命令行。命令行、共用动词、长度解析与按文件找标签在 `ely_office::remote`，各应用只写自己的动词；各命令所读所改的范围见 `docs/help.md`。
- ElyTable 的 R 宏（实验性，TABLE-17）：只在用户点运行时（首次与载入 .R 后先警告）以参数数组起 `Rscript --vanilla`，处理所选区域的类型化副本；R 不是沙箱，以用户权限运行，从不代装；停止、关对话框或 30 秒即整树结束；内核（补丁 0081）在一个撤销组里写回；日志不含代码、单元格值与 R 的输出。细则见 `docs/r-macros.md`。
- ElyMark 原生实现（组件库 Markdown 组件与其 Markdown 树），不用 CEF、Electron；Typora 只作参照，读同一文件不同时随 GitHub（GFM）。
- ElyMail：IMAP 与 POP3 由引擎自写，SMTP 用 mail-send；Microsoft 走 OAuth，客户端 ID 构建时注入（本机 `cred.txt`，CI 为组织机密）；发布构建（`scripts/ci.sh`）缺即失败，本机与 PR 构建缺时不注入，Microsoft 登录不可用；Gmail 与 iCloud 走应用专用密码，QQ 邮箱、163 邮箱、126 邮箱走授权码。网络随系统代理。
- ElyAgent 以 Rust 依赖直接嵌入 Kigi CLI，不用 ACP。
- 合并前：`.github/workflows/pr.yml` 在每个 PR 与 main 的推送上，以 GitHub 托管的 Ubuntu 建 MuPDF（PDF worker 才编得过）后跑 check.sh、deny.sh、panics.py（数量比 PR 的基线或推送前的提交）、整个工作区的 clippy（告警即败）、官网的单测（`site/test`，取全部发布标签）、发布规则的脚本与不需引擎的测试（严格模式）；PR 从不上自托管机器，带引擎的全部测试是发布的门（release-tests.sh）。
- 审查：每条任务交另一个模型审查，至多三轮（`scripts/review.sh`，herdr 右侧窗格里的 Pi，K3.1 Pro，思考 high）。

## 技术栈的细节

| 层 | 选型 |
| --- | --- |
| Mail | mail-send、mail-parser、mail-builder，IMAP（imap-proto 解析）与 POP3 由引擎自写（`crates/ely-mail-engine`，应用进程内的后台任务，无 worker）+ SQLite（FTS5）；网络随系统代理（HTTP CONNECT、SOCKS5）；正文以 html5ever 解析、净化后按块的子集由 GPUI 绘制；写信用 `documents::MarkdownDocument`，发出纯文本与 HTML（ElyMail 的 `markup.rs` 由 `documents::markdown_tree` 写出，链接照引擎读信的 `page::link`）；Microsoft 走 OAuth，Gmail 与 iCloud 走应用专用密码，QQ 邮箱、163 邮箱、126 邮箱走授权码 |
| Mark | 组件库 `documents::MarkdownDocument`（GPUI，原文即文本，无序列化）；组件库的 Markdown 树（`documents::mdast`，pulldown-cmark 建）解析与导出 HTML，RaTeX 公式，mermaid-rs-renderer 图；PDF 经 `ely-pdf-worker` 由 MuPDF 排版 |
