crates/ely-office/src/recover/slot.rs:25 (with crates/ely-office/src/recover/fit.rs:26) — A refused snapshot still marks its edit as written (`self.written = Some(edited)`), and `fit::recheck` clears only `refused`. So once the space is raised, `point_due` sees `written == edited` and that unsaved content never gets a point until the user types again. This breaks the documented "放得下即恢复写点" (decisions 2026-11-04) and PRD §6.3/PERF-10 "不丢数据". Scenario, reproduced in a probe copy (`.work/R15.46/probe-run.log`): open big.fodt, shrink the space to 1 MB, type "big", run a round, and the snapshot is refused (toast shown). Raise the space to 64 MB as the toast says, and the tick clears `refused`. Three more owed rounds with pauses follow, and the tab is still dirty: `points=0 writing=0`. Only one more key gives `points=1`. If the app crashes in that window, the edits are lost even though they now fit. The shipped test `over_its_space` hides this because it types "more" before raising the space. Fix: since `refused` already gates `point_due`, don't mark the refused edit as written (or reset `written` when `refused` clears). Add a test that raises the space with no further typing and expects a point.
